# 부하테스트 결과 (2026-11-18, #14)

동시 사용자 N명이 문제를 풀어 제출하고 AI 리뷰를 요청할 때, 채점 대기 시간과 AI 리뷰 대기 시간이 어떻게 늘어나는지 지금 운영 서버에서 쟀다.

## 1. 결과

현재 설정: 채점 슬롯 2, AI 동시 처리 5, GPU RTX A4000 1장. 표의 값은 중앙값 / 최대다.

| 동시 인원 | 2명 | 10명 | 30명 | 50명 | 100명 |
|---|---|---|---|---|---|
| 예제 실행 대기 | 1초 | 1초 / 6초 | 1초 / 34초 | 13초 / 42초 | 24초 / 46초 |
| 채점 대기 | 2초 / 7초 | 5초 / 9초 | 22초 / 35초 | 41초 / 49초 | 52초 / 1분 58초 |
| AI 코드 리뷰 대기 | 1분 33초 | 1분 44초 / 4분 4초 | 3분 40초 / 6분 53초 | 7분 15초 / 13분 24초 | 13분 / 26분 36초 |
| AI 오답 분석 대기 | 1분 43초 | 1분 50초 / 4분 4초 | 4분 39초 / 8분 58초 | 6분 31초 / 15분 9초 | 16분 48초 / 28분 12초 |
| AI 처리량 (건/분) | – | 2.2 | 3.0 | 3.2 | 3.3 |
| AI 실패 (응답 시간 초과) | 0 | 0 | 1 | 0 | 1 |

- 100명일 때 AI 요청 100건은 3분 안에 몰려 들어왔고, 모두 끝나는 데 30분이 걸렸다. 중앙값은 14.9분, 90%는 26.4분 안에 받았다.
- 100명의 AI 대기 시간은 DB의 요청·완료 시각으로 계산했다. k6 스크립트가 AI 결과를 20분까지만 기다려서 28명의 값이 잘렸기 때문이다.
- 혼자 제출했을 때 채점은 약 2초, 시간 초과 판정은 7~12초 걸렸다.

## 2. 채점 슬롯을 4로 늘린 결과

1절의 결과에서 채점 대기는 judge VM CPU가 놀고 있는데도 늘어났다. 그래서 채점 슬롯을 2에서 4로 늘리고 30·50·100명을 다시 쟀다(2026-11-19 00:10~01:20 KST).

- 운영 이미지(`3a33b33`)에서 `JudgeWorker.SLOTS`만 4로 바꾼 임시 이미지를 썼다. Judge0 `judge0.conf`의 `COUNT`도 4로 바꿨다. 나머지 조건은 1절과 같다.
- 100명의 AI 대기는 k6 스크립트가 60분까지 기다리도록 고친 뒤 k6 값으로 쟀다.

### 채점 대기 (중앙값 / 최대 / 90%)

| 동시 인원 | 슬롯 2 | 슬롯 4 |
|---|---|---|
| 30명 | 22초 / 35초 / 34초 | 7.5초 / 11초 / 10초 |
| 50명 | 41초 / 49초 / 47초 | 13.5초 / 24초 / 19초 |
| 100명 | 52초 / 1분 58초 / 1분 56초 | 29초 / 48초 / 45초 |

### 그 밖의 항목 (슬롯 4, 중앙값 / 최대)

| 동시 인원 | 30명 | 50명 | 100명 |
|---|---|---|---|
| 예제 실행 대기 | 1초 / 4초 | 3초 / 17초 | 8초 / 28초 |
| AI 코드 리뷰 대기 | 2분 58초 / 8분 15초 | 5분 47초 / 12분 12초 | 10분 24초 / 28분 25초 |
| AI 오답 분석 대기 | 6분 28초 / 10분 6초 | 8분 52초 / 14분 48초 | 19분 31초 / 29분 17초 |
| AI 실패 (응답 시간 초과) | 1 | 1 | 3 |
| 판정 불일치 | 0 | 0 | 0 |
| HTTP 요청 실패 | 0 / 10,907 | 0 / 23,621 | 1 / 93,698 |
| judge VM CPU (가장 바쁠 때 놀던 비율) | 3% | 2% | 2% |

- 채점 대기가 슬롯 2일 때의 1/2~1/3로 줄었다. 정답 코드가 시간 초과로 바뀌는 등의 판정 불일치는 없었다.
- 대신 judge VM CPU가 거의 다 찼다. 가장 바쁠 때 2~3%만 놀았다. 슬롯 2일 때는 47% 이상 놀았다. CPU 4개를 실행 칸 4개가 다 쓰는 상태라, 이 VM에서 슬롯을 더 늘려도 빨라지기 어렵다.
- AI 대기 시간은 슬롯과 관계없다. 측정마다 다른 것은 사용자의 쉬는 시간이 무작위라 AI를 누른 순서가 달라졌기 때문이다.
- 100명의 HTTP 실패 1건은 API 로그에 오류가 없었다. 테스트가 31분 걸려 로그인 토큰(30분)이 만료되면서 난 `401`로 보이며, 스크립트가 다시 로그인했다.

### 슬롯 4로 바꾸는 방법

측정 뒤 운영은 슬롯 2로 되돌렸다. 4로 적용할 때는 아래 두 값을 **같은 값으로** 함께 바꾼다. API만 늘리면 Judge0 안에서 줄을 서고, Judge0만 늘리면 칸이 논다.

1. API: `api/src/main/java/com/codingmon/api/judge/JudgeWorker.java`

   ```diff
   -    static final int SLOTS = 2;
   +    static final int SLOTS = 4;
   ```

   동시에 채점하는 제출 수(세마포어)와 채점 스레드 수를 이 값이 정한다. 상수라서 바꾸려면 이미지를 다시 빌드해 배포해야 한다(`infra/README.md`의 이미지 배포 절차).
2. Judge0: judge VM의 `judge/judge0.conf`

   ```diff
   -COUNT=2
   +COUNT=4
   ```

   conf는 마운트라 내용만 바꾸면 compose가 컨테이너를 다시 만들지 않는다. `docker compose up -d --force-recreate server workers`로 다시 띄운다. workers 컨테이너 안에 `resque-2.0.0: Waiting for 1.13.1` 프로세스가 4개 보이면 적용된 것이다.

적용 순서와 확인할 점은 다음과 같다.

- 진행 중인 채점이 없을 때 바꾼다(`submissions.job_status`가 `QUEUED`·`COMPILING`·`RUNNING`인 행이 0).
- judge VM은 4 vCPU라 슬롯 4에서 CPU가 거의 다 찬다. 이번 측정에서는 정답 코드가 시간 초과로 바뀌지 않았지만, 문제를 추가하거나 무거운 문제가 생기면 다시 확인한다. 정답이 시간 초과로 나오면 3으로 낮춘다.
- Judge0 대기열(`MAX_QUEUE_SIZE=100`)은 문제당 테스트케이스가 최대 10개라 4칸 × 10 = 40으로 여유가 있다.
- 메모리는 C++ 컴파일이 칸마다 최대 512MB라 4칸이면 약 2GB다. judge VM은 7.8GiB이고, 이번 측정 중 4.2GB 이상 남았다.
- `judge/README.md`에는 슬롯 2개를 전제로 쓴 설명이 있다(`COUNT`, `RAILS_SERVER_PROCESSES`, 메모리 여유, 큐 크기 근거). 바꿀 때 함께 고친다.
- 서버마다 값을 다르게 두려면 `SLOTS`를 설정값(예: `JUDGE_SLOTS`)으로 바꾸는 것이 낫다. 이번 측정에서는 상수만 바꿨다.

## 3. 알게 된 것

1. **AI가 가장 큰 병목이다.** GPU 1장으로는 분당 약 3.3건이 한계다. 사람이 늘어도 처리량은 더 늘지 않고, 기다리는 시간만 사람 수에 비례해 늘어난다. 실제 요청의 출력은 1,800~8,700토큰으로 편차가 커서, 출력을 2,000토큰으로 고정한 합성 측정(분당 5건)보다 처리량이 낮다.
2. **채점은 슬롯 2에서는 슬롯 수가, 슬롯 4에서는 CPU가 병목이다.** 슬롯 2일 때 혼자면 2초인 채점이 100명일 때 최대 2분까지 늘었고, 그동안 judge VM은 CPU가 절반 이상 놀았다. 슬롯은 API `JudgeWorker.SLOTS`와 Judge0 `COUNT`가 모두 2로 고정돼 있어 한 번에 2건만 처리한다. 슬롯을 4로 늘리면 비용 없이 대기가 1/2~1/3로 줄지만, judge VM CPU 4개가 다 찬다. 100명에서 90%가 45초라 목표(90%가 5초 안)를 맞추려면 judge 서버를 늘려야 한다.
3. **API와 DB는 여유가 있다.** 100명일 때도 응답 중앙값이 1ms 이하였고, 요청 약 9만 건 중 실패가 없었다.
4. **한 PC에 VM 3개를 둔 것은 지금 규모에서 문제가 되지 않았다.** 모든 단계에서 `st`가 0이었다.
5. **AI 응답 시간 초과가 가끔 난다.** 30명과 100명에서 1건씩 났다. 5건을 동시에 만들면 칸당 속도가 약 30 tok/s로 떨어진다. 그래서 답이 긴 요청은 API의 응답 제한 시간(`LLM_READ_TIMEOUT=180s`) 안에 끝나지 못한다. 줄에서 기다린 시간은 제한 시간에 들어가지 않고, Ollama가 만드는 시간만 들어간다.
6. **부하가 판정을 바꾸지 않았다.** 100명이 동시에 내도 정답 코드는 모두 `ACCEPTED`였다.

## 4. 테스트 조건

### 환경

운영 서버를 그대로 썼다. 세 VM은 PC 한 대(Proxmox)에서 돌아간다.

| VM | 사양 | 역할 |
|---|---|---|
| app | 4 vCPU / 7.8GiB | API·DB·웹 |
| judge | 4 vCPU / 7.8GiB | Judge0 채점 |
| llm | 8 vCPU / 31GiB + RTX A4000 16GB | Ollama `gemma4:12b` |

| 설정 | 값 |
|---|---|
| 채점 슬롯 | 2 (API `JudgeWorker.SLOTS`, Judge0 `COUNT`) |
| AI 동시 처리 | 5 (`LLM_WORKERS`, `OLLAMA_NUM_PARALLEL`) |
| AI 응답 제한 시간 | 180초 (`LLM_READ_TIMEOUT`) |
| AI 출력 상한 | 8,192토큰 (`LLM_MAX_OUTPUT_TOKENS`) |
| AI 줄 칸 수 | **테스트 때만 20 → 100** (`LLM_QUEUE_CAPACITY`). BUSY가 아니라 대기 시간을 재려고 늘림 |
| 채점 미완료 상한 | **테스트 때만 100 → 200** (`JUDGE_PENDING_LIMIT`) |

### 사용자와 시나리오

- 테스트 계정 100개(`lt001`~`lt100@loadtest.local`)를 DB에 직접 넣었다. 계정 하나가 사용자 한 명이다.
- 동시 인원은 2 → 10 → 30 → 50 → 100명 순서로 올렸다. 모두 같은 시각에 시작해, 각자 아래 흐름을 **한 번씩** 진행한다.
  1. 문제 목록 보기 → 3~10초 쉼
  2. 문제 보기 → 10~30초 쉼 (코드 작성)
  3. 예제 실행 → 결과가 나올 때까지 1초마다 확인
  4. 3~10초 쉼
  5. 제출 → 채점 결과가 나올 때까지 1초마다 확인
  6. 3~10초 쉼
  7. AI 요청 → 결과가 나올 때까지 1초마다 확인
- 쉬는 시간은 범위 안에서 무작위로 정한다. 확인 간격 1초는 웹 화면(`web/src/app/queryClient.ts`)과 같다.
- AI 기능은 실제 판정으로 고른다. 정답이면 코드 리뷰, 오답이면 오답 분석을 요청한다.

### 문제 선정과 코드

공개된 문제 26개를 모두 썼다. 코드는 64개이고, 사용자마다 하나씩 배정했다.

| 구분 | 출처 | Python | C++ | 설명 |
|---|---|---|---|---|
| 정답 32 | 사람 코드 | 6 | – | 팀원이 테스트 계정으로 직접 풀어 맞힌 제출. 참고 정답을 그대로 복사한 3개는 뺌 |
| | 참고 정답 | 20 | 6 | 관리자가 등록·검증한 정답. 사람 정답이 없는 문제와, C++ 오답을 만든 문제에 씀 |
| 오답 32 | 사람 코드 | 3 | – | 실제로 틀린 제출(DFS 실수, 오답, 시간 초과). 빈 템플릿이나 `print(a+b)`처럼 대충 낸 8개는 뺌 |
| | 만든 오답 | 24 | 5 | 문제마다 학습자가 흔히 하는 실수를 하나씩 넣음 |

- 만든 오답의 실수 종류
  - 경계값: 첫·마지막 원소 빠뜨림, `range` 끝을 하나 덜 씀
  - 조건 빠뜨림: 윤년 400년 규칙, 축 위의 점, 같은 횟수일 때 정렬
  - 느린 풀이: O(n²) → 시간 초과
  - C++: `int` 넘침, 조건을 반대로 씀
  - 출력 형식: 공백 하나 차이
- 만든 오답은 `input()`을 쓰는 학습자 스타일로 짰다. 참고 정답은 `def main()` 함수 형식이라 사람 코드와 스타일이 다르다.
- 사전 확인: 66개를 한 번씩 제출해 예상 판정이 나오는지 봤다. 64개는 예상대로 나왔다. 실제로는 맞은 만든 오답 2개(대소문자 뒤집기 Python, 평균보다 높은 점수 C++)는 뺐다.
- 배정: 홀수 번 사용자는 정답 32개, 짝수 번 사용자는 오답 32개에서 차례로 받는다.
  - 64명 이하면 모든 사용자가 다른 코드를 낸다.
  - 100명이면 쪽마다 18명이 같은 코드를 한 번 더 쓴다. 제출이 따로라 AI는 100건 모두 새로 만든다.
- 언어 비율은 Python 53개, C++ 11개(약 17%)다.

### 측정 방법

- 스크립트와 실행·되돌리기 방법은 [`../loadtest/README.md`](../loadtest/README.md)에 있다.
- k6 `0.54.0`을 app VM 안에서 Docker로 돌려 API(`http://api:8080`)에 직접 요청했다. Cloudflare tunnel은 거치지 않았다. 차이는 요청당 0.2초 이내로 추정해 생략했다.
- 대기 시간은 요청을 보낸 순간부터 결과가 끝날 때까지다. 예제 실행, 채점, AI 리뷰, AI 분석을 따로 쟀다.
- 로그인은 측정에서 빼려고 시작 전에 미리 했다.
- 서버 상태는 세 VM의 `vmstat -t 5`와 llm VM의 `nvidia-smi`(5초 간격)로 기록했다.

## 5. 한계

- 사람이 쓴 코드는 9개뿐이고, 나머지는 참고 정답과 직접 만든 오답이다.
- C++ 비율(17%)은 실제 사용자 비율이 아니라 코드 묶음 구성으로 정해진 값이다.
- 사용자 1명이 한 번씩만 풀이한다. 몇 시간 동안 계속 쓰는 부하는 재지 않았다.
- 전원이 같은 시각에 시작한다. 과제 마감 직전처럼 몰리는 상황에 가깝고, 평소보다 가혹한 조건이다.
- AI 줄을 100칸으로 늘려서 쟀다. 원래 설정(처리 중 5 + 줄 20 = 25)이면 동시에 25명이 넘게 요청할 때부터 BUSY가 나고, 100명이면 75명이 바로 BUSY를 받는다.
- llm VM CPU가 높게 쓰이는 원인은 확인하지 못했다.
