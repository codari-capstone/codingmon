# 협업 규칙 — AI 기반 코딩테스트 학습 플랫폼

Oct 3, 2026 · @찬우

3명이 10주 동안 같은 저장소에서 충돌 없이 개발하기 위한 팀 전체 규칙이다. 모든 작업은 GitHub 이슈에서 시작해 PR로 끝난다.

## 1. 결정 사항 한눈에

| 항목           | 결정                                                 |
| -------------- | ---------------------------------------------------- |
| 브랜치 전략    | 간소화 Git Flow (main·develop·feature)               |
| 커밋 메시지    | 타입 영어 + 설명 한글 + 이슈 번호                    |
| PR 병합        | 팀원 1명 승인 필수, 일반 merge                       |
| 작업·일정 관리 | GitHub Issues + Projects 보드                        |
| API 협업       | 명세 우선 (OpenAPI를 같이 작성한 뒤 구현)            |
| 변수명 표기법  | 분야별 자율, 단 API JSON·DB 이름은 공통 규칙         |
| 대화           | 디스코드, GitHub 알림 연동 없이 직접 알림            |
| 회의           | 주기는 상황에 따라 조정, 결정 사항은 회의록으로 남김 |
| 문서           | GitHub (README·Wiki·docs 폴더)                       |

## 2. 작업 흐름

기능 하나는 아래 순서로 진행한다. 예시는 기능명세서의 SOLVE-08(예제 실행)이다.

1. **이슈 만들기** — `[SOLVE-08] 예제 실행 화면` 이슈를 만들고 담당자·라벨·마일스톤을 정한다. 번호가 #12라고 하자.
2. **브랜치 만들기** — 최신 develop에서 `feature/12-sample-run`을 만든다.
3. **커밋하기** — `feat: 예제 실행 결과 비교 표 추가 (#12)`처럼 작은 단위로 자주 커밋한다.
4. **PR 올리기** — develop으로 PR을 열고 본문에 `Closes #12`를 적는다. 자동 검사(CI)가 통과하는지 확인한다.
5. **리뷰 요청** — 리뷰어를 지정하고 디스코드 #리뷰요청 채널에 PR 링크를 직접 올린다.
6. **수정과 승인** — 리뷰 의견을 반영하고 1명이 승인하면 작성자가 일반 merge한다.
7. **마무리** — 이슈가 자동으로 닫히고 보드에서 Done으로 옮겨지며, 병합된 feature 브랜치는 삭제한다.

## 3. 브랜치 전략

Git Flow에서 release·hotfix를 뺀 간소화 버전을 쓴다. 10주·3명 프로젝트에서는 배포 준비와 긴급 수정을 따로 관리할 만큼 배포가 잦지 않기 때문이다.

| 브랜치                      | 역할                                                                        | 만드는 곳 → 병합하는 곳 |
| --------------------------- | --------------------------------------------------------------------------- | ----------------------- |
| `main`                      | 발표·배포 가능한 버전. 마일스톤마다 develop을 병합하고 태그(v0.1 등)를 붙임 | develop → main          |
| `develop`                   | 다음 버전을 모으는 통합 브랜치. 항상 실행 가능한 상태 유지                  | —                       |
| `feature/{이슈번호}-{설명}` | 기능 개발·버그 수정 등 모든 작업                                            | develop → develop       |

### 규칙

- 브랜치 이름은 영어 소문자와 하이픈만 쓴다. 예: `feature/12-sample-run`, `feature/27-fix-poll-stop`
- main과 develop에는 직접 push하지 않는다. GitHub 브랜치 보호 규칙으로 ‘PR 필수, 승인 1명, CI 통과’를 걸어 둔다.
- feature 브랜치는 짧게 유지한다. 2\~3일 안에 PR을 올릴 수 있는 크기로 이슈를 나눈다.
- 작업 중 develop이 바뀌면 `git merge develop`으로 내 브랜치에 반영한 뒤 PR을 올린다. 충돌은 브랜치 주인이 해결하고, 상대 코드가 걸리면 해당 팀원과 함께 확인한다.
- main으로의 병합은 계획서 마일스톤(4·6·7·9·10주차)에 맞추고, 병합 전에 시연 흐름을 한 번 돌려 본다.

## 4. 커밋 컨벤션

형식은 `타입: 한글 설명 (#이슈번호)`이다.

```text
feat: 힌트 패널 단계별 열기 추가 (#21)
fix: 채점 완료 후 폴링이 멈추지 않는 문제 수정 (#27)
```

| 타입       | 쓰는 경우                                                              |
| ---------- | ---------------------------------------------------------------------- |
| `feat`     | 새 기능 추가                                                           |
| `fix`      | 버그 수정                                                              |
| `refactor` | 동작은 그대로 두고 코드 구조 개선                                      |
| `style`    | 코드 모양만 변경 (포맷, 세미콜론 등). 화면 디자인 변경은 feat 또는 fix |
| `test`     | 테스트 추가·수정                                                       |
| `docs`     | 문서 수정 (README, API 명세, 회의록)                                   |
| `chore`    | 빌드·패키지·설정 등 기능과 무관한 작업                                 |
| `ci`       | GitHub Actions·배포 스크립트 변경                                      |

### 규칙

- 설명은 50자 안쪽으로, ‘\~추가’, ‘\~수정’처럼 무엇을 했는지 쓴다. 마침표는 붙이지 않는다.
- 커밋 하나에는 변경 하나만 담는다. 기능 추가와 포맷 정리를 같이 커밋하지 않는다.
- 이유를 남겨야 하면 한 줄 띄고 본문에 적는다.
- 일반 merge를 쓰므로 작업 중 커밋이 develop 기록에 그대로 남는다. ‘수정’, ‘wip’ 같은 의미 없는 메시지를 쓰지 않는다.

## 5. 이슈·일정 관리

모든 작업은 GitHub 이슈로 만들고, Projects 보드 하나에서 진행 상황을 본다.

### 이슈 작성

- 제목은 기능명세서 ID를 앞에 붙인다. 예: `[RES-01] 채점 진행률 폴링`. 명세서에 없는 작업은 `[설정]`, `[버그]`처럼 분류를 붙인다.
- 템플릿은 기능과 버그 두 가지다. 기능은 ‘목적 / 할 일 체크리스트 / 완료 조건’, 버그는 ‘재현 방법 / 기대 동작 / 실제 동작 / 스크린샷’을 적는다.
- 이슈 하나는 2\~3일 안에 끝낼 수 있는 크기로 나눈다.

### 라벨

| 종류     | 라벨                                    |
| -------- | --------------------------------------- |
| 분야     | `FE`, `BE`, `채점·AI`, `인프라`, `공통` |
| 유형     | `기능`, `버그`, `문서`, `설정`          |
| 우선순위 | `필수`, `선택` (기능명세서와 동일)      |
| 상태     | `막힘` (다른 작업을 기다리는 중)        |

### Projects 보드

| 칸          | 의미                         |
| ----------- | ---------------------------- |
| Backlog     | 아직 일정을 정하지 않은 작업 |
| Todo        | 이번 주에 할 작업            |
| In Progress | 브랜치를 만들고 진행 중      |
| In Review   | PR을 올리고 리뷰 대기 중     |
| Done        | 병합 완료                    |

### 마일스톤

계획서의 마일스톤을 GitHub 마일스톤으로 만들고 모든 이슈를 하나에 연결한다.

| 마일스톤 | 기한          | 목표                           |
| -------- | ------------- | ------------------------------ |
| M1       | 1주차 (10/4)  | DB 스키마·API 명세 확정        |
| M2       | 4주차 (10/25) | 제출 → 판정·쉬운 설명          |
| M3       | 6주차 (11/8)  | AI 분석 → 단계별 힌트 → 재제출 |
| M4       | 7주차 (11/15) | 학습 리포트·추천 포함 MVP 고정 |
| M5       | 9주차 (11/29) | AWS 배포와 사용자 검증         |
| M6       | 10주차 (12/6) | 문서화·발표·시연               |

## 6. PR·코드 리뷰

### PR 올리기

- 제목은 커밋과 같은 형식으로 쓴다. 예: `feat: 힌트 패널 단계별 열기 (#21)`
- 변경량은 되도록 400줄 이하로 유지한다(자동 생성 파일 제외). 커지면 이슈를 나눈다.
- 작업 중에 의견을 받고 싶으면 Draft PR로 올린다.
- 본문은 아래 템플릿을 따른다. `.github/pull_request_template.md`에 넣어 두면 자동으로 채워진다.

```markdown
## 관련 이슈

Closes #

## 변경 내용

-

## 확인 방법

1.

## 스크린샷 (화면 변경 시)

## 체크리스트

- [ ] 로컬에서 실행해 보았다
- [ ] 테스트를 추가하거나 필요 없는 이유를 적었다
- [ ] API가 바뀌었다면 명세를 먼저 고쳤다
```

### 병합 조건

1. CI(빌드·타입 검사·린트·테스트) 통과
2. 작성자가 아닌 팀원 1명 이상 승인
3. 모든 리뷰 대화가 해결됨(Resolve)
4. 조건을 만족하면 **작성자가 직접 일반 merge**하고 브랜치를 삭제한다

### 리뷰하기

- 리뷰어는 가능한 한 다른 분야 팀원도 돌아가며 맡는다. 서로의 코드를 알아야 발표와 장애 대응이 수월하다.
- 의견에는 접두어를 붙여 무게를 알린다.

| 접두어   | 의미                                                  |
| -------- | ----------------------------------------------------- |
| `[필수]` | 고치지 않으면 승인하지 않음 (버그, 보안, 명세 불일치) |
| `[제안]` | 더 나은 방법 제안. 반영 여부는 작성자가 결정          |
| `[질문]` | 이해를 위한 질문                                      |

- 코드를 평가하고 사람을 평가하지 않는다. ‘왜 이렇게 했어요?’보다 ‘이 부분은 \~하면 어떨까요?’로 쓴다.
- 리뷰 요청은 GitHub 알림 연동 없이 디스코드 #리뷰요청에 PR 링크를 직접 올려 알린다.

## 7. API 협업 (명세 우선)

API는 코드보다 명세를 먼저 쓴다. 명세가 확정되면 백엔드는 그대로 구현하고, 프론트엔드는 같은 명세로 타입과 가짜 API(MSW)를 만들어 동시에 개발한다.

### 명세 파일

- 저장소의 `contracts/openapi.yaml` 하나를 기준으로 삼는다(OpenAPI 3). CODEOWNERS가 `/contracts/`를 세 명 공동 리뷰로 잡아 두었고, 프론트엔드의 `npm run gen:api`도 이 경로를 읽는다.
- 1주차에 세 명이 함께 핵심 API(인증, 문제, 제출·채점, AI 분석·힌트)를 작성하고 M1 마일스톤으로 확정한다. 나머지 API는 해당 기능을 시작하기 전에 같은 방식으로 추가한다.
- 백엔드가 Swagger UI를 띄우더라도 기준은 이 파일이다.

### 명세 변경 절차

1. 변경이 필요한 사람이 `openapi.yaml`만 고친 PR을 올린다(커밋 타입 `docs`).
2. 그 API를 쓰는 쪽(보통 프론트엔드와 백엔드 둘 다)이 승인해야 병합한다.
3. 병합 후 디스코드 #공지에 바뀐 API를 한 줄로 알린다.
4. 백엔드는 구현을 고치고, 프론트엔드는 `npm run gen:api`로 타입을 다시 만들고 MSW 응답을 고친다.

구현 도중 명세와 다르게 만들어야 할 이유가 생기면, 코드를 먼저 바꾸지 않고 이 절차로 명세부터 고친다.

### 공통 형식

| 항목            | 규칙                                      | 예시                                                    |
| --------------- | ----------------------------------------- | ------------------------------------------------------- |
| 경로            | `/api`로 시작, 복수형 명사, 소문자·하이픈 | `/api/problems/{id}`, `/api/submissions/{id}/ai-review` |
| JSON 필드       | camelCase                                 | `lineStart`, `evidenceType`, `revealedHintLevel`        |
| 고정된 값(enum) | 대문자 스네이크                           | `WRONG_ANSWER`, `FACT`, `HIDDEN`                        |
| 날짜·시간       | ISO 8601, UTC                             | `2026-10-03T06:15:41Z`                                  |
| 오류 응답       | RFC 9457 (Problem Details)                | `{ "type", "title", "status", "detail" }`               |
| 목록 조회       | page·size 쿼리, 응답에 전체 개수 포함     | `?page=0&size=20`                                       |

## 8. 코드 컨벤션

표기법과 스타일은 분야별로 담당자가 정하되, 두 분야가 만나는 곳(API JSON, DB)은 공통 규칙을 따른다. 각 분야는 규칙을 포맷터·린터 설정으로 자동화해 리뷰에서 모양을 두고 논쟁하지 않게 한다.

### 공통

| 대상           | 규칙                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------- |
| API JSON 필드  | camelCase (7장)                                                                                          |
| DB 테이블·컬럼 | snake\_case, 테이블은 복수형 (ERD와 동일: `problem_versions`, `revealed_hint_level`)                     |
| 비밀값         | 코드·커밋에 넣지 않음. `.env`는 `.gitignore`에 넣고 `.env.example`만 공유, 운영 값은 SSM Parameter Store |
| 주석           | ‘무엇을’보다 ‘왜’를 적음. 한글 허용                                                                      |

### 프론트엔드 (TypeScript·React)

React는 대문자로 시작하는 이름을 컴포넌트로 취급하므로, 컴포넌트·타입은 PascalCase, 변수·함수는 camelCase로 나눈다.

| 대상               | 표기법             | 예시                           |
| ------------------ | ------------------ | ------------------------------ |
| 컴포넌트와 그 파일 | PascalCase         | `HintPanel`, `HintPanel.tsx`   |
| 타입·인터페이스    | PascalCase         | `SubmissionResult`, `Verdict`  |
| 변수·함수          | camelCase          | `hintLevel`, `fetchProblem`    |
| 커스텀 훅          | use + camelCase    | `useSubmissionPolling`         |
| 상수               | UPPER\_SNAKE\_CASE | `MAX_HINT_LEVEL`               |
| 폴더               | 소문자·하이픈      | `features/ai`, `components/ui` |

포맷은 Prettier, 검사는 ESLint로 자동 적용한다.

### 백엔드·채점·AI

담당자가 정해 이 절에 추가한다. Java는 보통 클래스 PascalCase, 변수·메서드 camelCase, 패키지 소문자를 따른다.

## 9. 소통·회의·문서

### 디스코드 채널

| 채널                         | 용도                                                             |
| ---------------------------- | ---------------------------------------------------------------- |
| #공지                        | 회의 일정, 결정 사항, API 명세 변경 알림                         |
| #일반                        | 자유 대화                                                        |
| #리뷰요청                    | PR 링크와 리뷰어 멘션, 병합 완료 알림                            |
| #프론트 · #백엔드 · #채점-ai | 분야별 질문과 진행 공유                                          |
| #막힘                        | 혼자 해결하기 어려운 문제. 에러 메시지와 시도한 방법을 같이 적음 |
| 음성 채널                    | 회의, 페어 디버깅                                                |

### 소통 규칙

- 디스코드에서 정한 것은 디스코드에만 두지 않는다. 작업은 이슈로, 규칙·명세는 docs 문서로 옮겨 적는다.
- GitHub 알림을 연동하지 않으므로, 리뷰 요청·병합·명세 변경은 본인이 해당 채널에 직접 올린다.
- 하루 이상 막히면 #막힘에 올리고 이슈에 `막힘` 라벨을 붙인다.

### 회의

- 주기와 방식은 상황에 따라 정하고 #공지에 미리 알린다. 계획서의 주간 미팅 시연은 유지한다.
- 회의에서는 보드를 함께 보며 지난 회의 이후 한 일, 다음에 할 일, 막힌 점을 확인한다.
- 회의록은 돌아가며 쓰고 `docs/meetings/YYYY-MM-DD.md`에 남긴다. 항목은 참석자, 결정 사항, 할 일(담당·기한)이다.

### 문서 위치

| 위치        | 담는 내용                                                                        |
| ----------- | -------------------------------------------------------------------------------- |
