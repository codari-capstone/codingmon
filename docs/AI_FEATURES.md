# AI 기능 정의

2026-09-27 확정. 이 문서가 AI 기능의 기준이며, 계획서(FINAL_PLAN·양식본)의 AI 관련 내용과 다르면 이 문서를 따른다.

## 1. 원칙

1. **기본 채점은 백준과 같다.** 판정 종류(백준과 같은 9가지, 10절)와 채점 진행률만 알려 주고, 판정마다 쉬운 설명을 AI 없이 붙인다. 몇 번째 비공개 테스트에서 틀렸는지, 그 입력과 기대 출력은 공개하지 않는다. 컴파일 에러의 컴파일러 메시지는 백준처럼 보여 주고, 공개 예제에서 난 런타임 에러 원문도 보여 준다.
2. **AI는 사용자가 요청할 때만 개입한다.** 채점만으로 충분한 사용자는 AI 없이 풀 수 있다.
3. **AI는 정답 코드를 주지 않는다.** 틀린 이유와 사고 흐름, 문제를 푸는 원리(수학적 규칙·개념)를 설명한다. 정답 코드 보기 기능은 두지 않는다.
4. **사실과 추정을 구분한다.** 실행 결과로 확인된 내용은 [사실], AI가 코드에서 짐작한 원인은 [추정]으로 표시한다. 화면 배지는 [사실]을 [실행 결과], [추정]을 [코드 분석]으로 표시하고, [코드 분석] 문장은 단정하지 않는 말투('~것 같습니다', '~일 가능성이 높아요')로 쓴다.
5. **추천은 규칙이, 설명은 AI가 맡는다.** 어떤 문제를 추천할지는 풀이 통계로 서버가 정하고, AI는 그 결과를 사람이 읽을 수 있는 분석과 개념 설명으로 바꾼다.

공개 예제는 문제에 적힌 공개 데이터이므로, 예제 실행 결과(기대 출력과 실제 출력 비교)는 AI 없이도 보여 준다.

## 2. 기능 목록

| # | 기능 | 언제 | 사용자에게 보이는 것 |
|---|---|---|---|
| F1 | 오답 원인 분석 | 정답이 아닌 판정 후 **[AI 분석]** 버튼 | 틀린 이유와 틀린 부분(줄 번호)이 바로 표시됨 |
| F2 | 단계별 힌트 | F1 이후 **[힌트 보기]**를 누를 때마다 한 단계씩 | 1단계 관찰 → 2단계 방향 → 3단계 원리. 정답 코드 없음 |
| F3 | 코드 리뷰 | 정답 후 **[AI 리뷰]** 버튼 | 시간·공간 복잡도, 개선점, 다음에 배울 개념 |
| F4 | 학습 리포트 + 다음 문제 추천 | 학습 기록 화면의 **[리포트 보기]** | 취약 개념(통계), AI 분석 문장과 개념 설명, 추천 문제 3개 |

## 3. F1 오답 원인 분석

판정별로 AI가 설명하는 내용은 다음과 같다.

| 판정 | AI 설명 |
|---|---|
| 컴파일 에러 | 컴파일러 메시지를 쉬운 말로 풀이하고 해당 줄을 짚는다 |
| 런타임 에러 | 에러 종류(인덱스 범위 초과, 0으로 나누기, 재귀 깊이 등)와 원인이 될 만한 줄 |
| 시간 초과 | 입력 제한 대비 반복 횟수로 본 복잡도 문제 |
| 메모리 초과 | 메모리를 많이 쓰는 자료구조·재귀 |
| 틀렸습니다 | 출력 형식 문제인지 로직 문제인지, 실패한 경우의 특성(가장 작은 입력, 큰 입력 등)과 의심되는 줄 |
| 출력 형식이 잘못되었습니다 | 답은 맞는데 요구한 모양과 다른 곳(줄 끝 공백, 빠지거나 더해진 빈 줄, 구분 문자) |
| 출력 초과 | 출력하는 반복문이 제때 끝나는지, 디버깅용 출력이 남았는지 |

- AI에 전달하는 것: 문제 설명·제약, 제출 코드, 판정, 공개 예제 실행 결과, 컴파일 메시지, 런타임 메시지(공개 예제 케이스만. 비공개 케이스는 런타임 에러 종류만), 실패한 비공개 테스트의 **특성**(원문 값은 전달하지 않음), 문제의 개념 태그.
  - 비공개 테스트의 특성은 통과·실패 개수, 판정별 실패 수, 런타임 에러 종류, 입력 크기 등급별 통과·실패 수, 가장 작은·큰 입력에서 실패했는지다. 크기 등급은 같은 버전 비공개 케이스의 입력 바이트 수를 로그 눈금으로 셋(작음·중간·큼)으로 나눈 것이다. 가장 큰 입력이 가장 작은 입력의 2배가 안 되면 모두 중간으로 본다. 케이스 순번과 정확한 입력 길이는 보내지 않는다.
  - 코드에는 줄 번호를 붙인다. 지문·코드·예제 출력은 모델 컨텍스트에 맞춰 항목마다 상한까지만 보내고, 자른 곳에 생략 표시를 남긴다. 글자 수는 JSON에 쓰일 길이로 센다. 예제는 실행한 전체 수와 실패 수를 함께 보내고, 상한보다 많으면 틀린 예제부터 고른다(`api`의 `AnalysisInput`).
- 비공개 테스트의 입력·기대 출력 값은 AI 응답에도 나오지 않는다(원칙 1).
- 버튼을 누르면 원인 설명과 힌트 3단계를 **한 번의 AI 호출로 함께 생성해 서버에 저장**한다. 원인 설명만 바로 보내고 힌트는 사용자가 요청한 단계까지만 보낸다. 브라우저에 미리 내려보내지 않는다.
- 응답은 요약, 의심 줄 번호, [사실]·[추정] 항목, 힌트 3단계(관찰·방향·원리)다(`api`의 `AnalysisResult`). 프롬프트는 `api/src/main/resources/prompts/analysis-<버전>/`에 공통 지시(`system.md`)와 판정별 지시(`<판정>.md`)로 두고, 고치면 새 버전 폴더를 만든다(8절 결과 재사용).

## 4. F2 단계별 힌트

| 단계 | 내용 | 기준 |
|---|---|---|
| 1단계 관찰 | 무엇을 비교하거나 확인해 볼지 | 실행 결과로 확인 가능한 사실에서 출발 |
| 2단계 방향 | 어디를 어떤 방향으로 바꾸면 되는지 | “조건식”, “반복 범위”처럼 고칠 위치와 방향만 |
| 3단계 원리 | 문제를 푸는 원리(수학적 규칙·알고리즘 개념) | 식과 말로 설명하고, 코드는 쓰지 않음 |

- 3단계가 마지막이다. 그 뒤에도 못 풀면 다시 제출하고 새로 분석을 요청한다.
- 몇 단계까지 열었는지 기록해 F4 리포트의 통계로 쓴다.

## 5. 예시: 역방향 피라미드

문제: 정수 n을 입력받아 별 피라미드를 거꾸로 출력한다. n = 3이면 다음과 같다.

```
*****
 ***
  *
```

학습자는 정방향 피라미드(별이 1개, 3개, 5개로 늘어나는 모양)를 구현해 제출했다.

1. **기본 채점**: `틀렸습니다`만 표시된다.
2. **[AI 분석]**
   - [사실] 공개 예제 1에서 기대 출력은 줄마다 별이 5개, 3개, 1개로 줄어드는데, 제출 코드의 출력은 1개, 3개, 5개로 늘어납니다.
   - [추정] 4번째 줄의 반복과 별 개수 식이 정방향 기준으로 작성된 것 같습니다.
3. **[힌트 1단계 관찰]** 예제 출력의 첫 줄과 마지막 줄 별 개수를 세어 보세요. 내 출력과 순서가 어떻게 다른가요?
4. **[힌트 2단계 방향]** 줄 번호 i가 커질 때 별 개수가 어떻게 변해야 하는지 식으로 적어 보세요. 조건식(반복 범위)이나 별 개수 식을 바꾸면 됩니다.
5. **[힌트 3단계 원리]** 정방향의 i번째 줄은 역방향의 (n − i + 1)번째 줄과 같습니다. 정방향 별 개수 2i − 1에서 i 자리에 n − i + 1을 넣으면 별은 2(n − i) + 1개, 앞 공백은 i − 1개가 됩니다.

## 6. F3 코드 리뷰

- 정답 제출에 한해 요청할 수 있다.
- 내용: 시간·공간 복잡도 추정과 문제가 의도한 복잡도 비교, 가독성·중복 등 개선점, 다음에 배울 개념.
- 개선 방향은 설명으로 제시하고, 다시 작성한 전체 코드는 주지 않는다.
- “다음에 배울 개념”은 F4 리포트에 참고 자료로 넘긴다.

**입력과 출력**(`prompts/code-review-<버전>/`, `CodeReviewResult`)

- 입력은 문제(지문·입출력 설명·제약·시간/메모리 제한·개념 태그)와 제출(언어·실행 시간·메모리·줄 번호를 붙인 코드)이다. 정답 제출이라 예제와 비공개 테스트는 모두 통과했으므로 보내지 않는다.
- 출력은 요약, 복잡도(근거 → 시간 → 공간 → 의도한 시간 → 비교 → 의도와 같거나 더 좋은지), 개선점 0~5개, 다음 개념 1~3개(짧은 개념 이름과 이유)다. 모델이 근거를 먼저 쓰고 결론을 뒤에 쓰도록 이 순서로 묻는다.
- 문제에는 의도한 복잡도가 적혀 있지 않다. 모델이 제약의 입력 최대 크기·시간 제한·개념 태그로 어림한 추정이고, 응답에도 추정이라고 밝힌다.
- 함수·메서드·변수 이름은 괄호 없이 이름만 쓰고(예: "sorted 함수"), 코드 위치는 줄 번호로 짚는다. 다음 개념 이름은 함수·라이브러리 이름이 아니라 개념 이름이다(예: "이분 탐색"). 모델은 태그 목록을 모르므로 개념 태그와는 서버가 맞춘다(아래).
- 결과는 `ai_reviews`(`review_type = CODE_REVIEW`)에 저장하고 같은 제출·같은 프롬프트 버전이면 다시 쓴다. 정답 코드 검사(8절)는 알고리즘 이름 규칙만 빼고 F1·F2와 같이 적용한다. 학습자는 이미 맞혔고, 리뷰는 다음에 배울 개념의 이름을 알려 주는 것이 목적이다.
- 결과를 `COMPLETED`로 저장하는 트랜잭션에서 다음 개념을 모든 개념 태그와 맞춰 `ai_review_next_concepts`에 함께 저장한다(`ConceptTagMatcher`, #83). F4가 사용자별로 모아 읽는다.
  - ① 이름이나 slug가 똑같은 태그 ② 띄어쓰기·대소문자만 다른 태그 ③ 같은 별칭 묶음의 태그(예: "이진 탐색"→"이분 탐색", "DP"→"동적 계획법") 순서로 보고, 한 단계에서 후보가 하나일 때만 잇는다. 후보가 둘 이상이면 잇지 않는다. 일부만 같은 이름("반복문 범위"와 "반복문")도 잇지 않는다.
  - 별칭 묶음(`ConceptAliases`)은 정답 코드 검사와 같이 쓴다. "메모이제이션"→"동적 계획법"처럼 가까운 개념도 같은 태그로 본다.
  - 이름과 이유는 태그와 맞든 안 맞든 원문 그대로 둔다. 맞춘 태그는 저장할 때 정하고, 뒤에 태그가 늘어도 다시 맞추지 않는다.
  - 이 표를 만들기 전에 끝난 리뷰는 마이그레이션(V4)이 원문만 옮기고 태그는 비워 둔다.
  - 차단된 결과에는 저장하지 않는다. 저장하지 못하면 결과도 저장하지 않고 `FAILED`가 된다(다시 요청할 수 있다). 리뷰 응답(API)에는 맞춘 태그를 싣지 않는다.
- 정답 제출 샘플 5개로 평가한 결과는 #82에 있다(`CodeReviewPromptIntegrationTest`).

## 7. F4 학습 리포트와 다음 문제 추천

**데이터**

- 문제마다 개념 태그 1~3개(예: 반복문 범위, 조건문, 인덱스 변환, 누적합). 팀이 문제를 등록할 때 붙인다.
- 제출 이력(판정, 시도 횟수), 힌트를 연 단계, AI 분석 요청 여부.

**규칙(서버가 계산)**

- 태그별로 해결률, 평균 시도 횟수, 평균 힌트 단계를 구한다. 문제의 태그는 공개 중인 버전을 따르고, 공개가 내려간 문제는 마지막으로 공개됐던 버전을 따른다. 시도 횟수는 문제마다 첫 정답까지의 제출 수(맞히지 못했으면 지금까지의 제출 수)다. 힌트 단계는 문제마다 첫 정답까지 연 가장 높은 단계(열지 않았으면 0)다.
- 취약 점수 = 0.5 × (1 − 해결률) + 0.3 × (평균 힌트 단계 / 3) + 0.2 × (min(평균 시도 − 1, 4) / 4). 가중치는 더미데이터로 조정한다.
- 취약 개념은 취약 점수 상위 2개 태그다. 점수가 0이면 취약 개념으로 보지 않는다. 점수가 같으면 낸 문제가 많은 태그, 그다음 slug 순으로 앞에 둔다. 해결률·평균 시도·평균 힌트 단계·취약 점수는 소수 둘째 자리까지 사사오입하고(예: 0.483 → 0.48, 0.485 → 0.49), 취약 점수는 반올림한 해결률·평균 힌트 단계·평균 시도로 계산한다. 순서와 취약 개념은 반올림한 점수로 정한다.
- 추천: 취약 점수가 높은 태그부터 아직 맞히지 않은 문제를 쉬운 순으로 3개 고르고, 모자라면 도전 문제로 채운다. 해당 태그의 쉬운 문제를 이미 풀었다면 한 단계 어려운 문제를 고른다.
  - 후보는 지금 공개 중이고 아직 맞히지 않은 문제다. 냈지만 틀린 문제도 넣는다. 근거 태그는 그 문제의 공개 버전에 붙어 있어야 한다.
  - 1위 태그에서 2개, 2위 태그에서 1개를 고른다. 자리가 남으면 1위의 남은 후보, 그다음 2위의 남은 후보에서 고르고, 그래도 남으면 점수가 0보다 큰 3위 이하 태그에서 차례로 고른다.
  - 그래도 3개가 안 되면 태그와 관계없이 `MEDIUM` → `HARD` → `EASY` 순으로 도전 문제를 채운다. 도전 문제에는 근거 태그가 없다. 공개 문제를 거의 다 맞혔을 때만 3개보다 적다.
  - 태그 안에서는 쉬운 순, 같은 난이도면 문제 번호 순이다. 태그가 여러 개인 문제는 한 번만 담고, 먼저 고른(순위가 높은) 태그의 추천으로 친다.
  - 추천은 리포트를 만들 때 함께 계산해 저장한다. 리포트를 보여 줄 때는 추천 문제마다 그 시점의 풀이 상태(`SOLVED`·`WRONG`·`UNSOLVED`)를 함께 준다.
- 서로 다른 문제를 5개 이상 맞혀야 리포트를 만든다. 통계에는 맞히지 못한 문제도 포함한다.

**AI(문장화)**

- 입력(`LearningReportInput`)은 서버가 계산한 통계(JSON), 서버가 고른 추천 문제, F3의 “다음 개념” 기록이다(#84).
  - 통계: 맞힌 문제 수와 개념별 이름·취약 여부·낸 문제 수·맞힌 문제 수·해결률·평균 시도·평균 힌트 단계. 취약한 순서 그대로다. 수치는 화면 표기 그대로 문자열로 준다(해결률 0.49 → `"49%"`, 1.50 → `"1.5"`). 모델이 계산하지 않게 하고 수치 대조(아래)도 이 값을 기준으로 한다. 취약 점수와 slug는 넣지 않는다.
  - 추천: 순위, 문제 제목, 난이도(쉬움·보통·어려움), 근거 취약 개념(도전 문제는 없음), 냈지만 아직 못 맞힌 문제인지.
  - 다음 개념: `NextConceptRepository.findRecent(사용자, 리뷰 수)`로 읽는다. 최근 코드 리뷰 N개(1~100, 제출마다 마지막 결과 하나)의 개념을 원문 이름·이유, 맞춘 태그(없으면 null), 문제와 함께 준다. 같은 개념이 여러 리뷰에 나오면 그대로 여러 번 나오므로 모으는 것은 리포트가 한다. 리포트는 최근 리뷰 10개를 읽어 같은 태그(태그가 없으면 띄어쓰기·대소문자만 다른 같은 이름)끼리 모으고, 많이 나온 순으로 5개까지 이름·횟수·문제 제목 3개·가장 최근 이유를 넣는다.
- 출력(`LearningReportResult`)은 취약 개념마다 설명과 연습 방법, 추천 문제마다 추천 이유, 요약 분석 문장이다. 지시는 `prompts/learning-report-<버전>/system.md`다.
  - 추천 이유는 AI가 쓰고 리포트 내용(`learning_reports.content`)에 순위별로 저장한다. 추천 행은 AI 응답 전에 저장해야 해서 `learning_report_recommendations`에는 이유 열을 두지 않는다(#85에서 지웠다). 가드레일에 걸린 이유 문장은 빼고 화면은 서버 값인 개념·점수만 보여 준다(REP-04). 서버가 만든 문구로 채우지 않는다(#84 논의).
- AI는 추천 목록과 수치를 바꿀 수 없다. 화면의 수치는 서버 값을 그대로 쓰고, AI 문장 안의 수치는 서버가 통계와 대조한다.
  - 응답 스키마는 입력마다 만든다. 취약 개념과 추천은 입력과 같은 개수만(minItems = maxItems), 개념 이름과 순위는 입력에 있는 값만(enum) 쓰게 해서 모델이 목록을 빼거나 늘리거나 바꾸지 못한다. 순서와 되풀이는 서버가 입력 순서로 맞춘다(`LearningReportResult.alignedTo`). 같은 개념이나 순위를 되풀이해 맞출 수 없으면 `FAILED`(`INVALID_RESPONSE`)로 두고 다시 만들지 않는다. 다음 요청에서 다시 만든다.
  - 지시에서 수치는 입력의 표기 그대로만 쓰고 새로 계산한 수를 쓰지 않게 하며, 글 하나에 두 개까지로 줄인다.
- **수치 대조**(`ReportNumberCheck`, #85): 저장하기 전에 AI 문장 속 수치를 통계와 대조해, 맞지 않는 수가 있는 문장을 지운다. 모델이 원래 어느 값을 뜻했는지 알 수 없으므로 고치지 않는다. 글의 문장이 모두 지워지면 그 글은 비고(null) 화면은 서버 값만 보여 준다. 이 검사로는 다시 만들지 않는다.
  - 보는 수: 백분율("50%", "50 퍼센트"), 소수("1.5"), 횟수·개수 단위가 붙은 정수("4문제", "3번", "2회", "2개", "3차례"). "2번째"(순서), "2단계"(힌트 단계 이름), 단위가 없는 정수, 한글로 쓴 수("두 번")는 보지 않는다. 문제 제목과 개념 이름 속 숫자("2차원 배열")는 가리고 본다. 값으로 비교하므로 표기만 다른 같은 값("1.50번")은 맞는 것으로 본다.
  - 글마다 쓸 수 있는 값이 다르다. 취약 개념의 설명·연습 방법은 그 개념의 통계, 추천 이유는 근거 개념의 통계(도전 문제는 없음), 요약은 모든 개념의 통계와 다음 개념을 권한 리뷰 수다. 맞힌 문제 수, 취약 개념 수, 추천 수는 어느 글에서나 쓸 수 있다. 다른 개념의 수치를 끌어다 쓴 문장도 지운다.
  - 내역은 `learning_reports.content`의 `numberCheck`(규칙 버전, 지운 문장 수, 비워진 글 수, `규칙@위치` 목록)에 저장하고 API에는 넣지 않는다. `report-number-check` 로그에도 한 줄씩 남긴다. 둘 다 응답 글은 남기지 않는다.
- 리포트는 사용자당 하루(UTC 날짜) 1회 새로 만들고, 그 사이에는 저장된 결과를 보여 준다(`POST`·`GET /api/users/me/learning-report`).
  - 통계와 추천은 만들기 시작할 때 계산해 `learning_reports.statistics`와 `learning_report_recommendations`에 저장하고, 화면의 수치와 추천 목록은 이 값을 쓴다. AI 응답에서 가져오지 않으므로 만드는 중이거나 실패해도 보인다.
  - AI 호출은 분석·리뷰와 같은 처리기(`AiWorker`)에서 돈다. 만들지 못한 이유(`failureReason`)와 처리 중에 서버가 내려간 경우는 분석·리뷰와 같다(8절 장애 대응). `FAILED`는 같은 날 다시 요청하면 같은 행으로 다시 만들고, 이때 통계와 추천도 다시 계산한다.

## 8. 공통 가드레일

- **정답 코드 금지**: F1·F2·F3 응답에 코드 블록을 쓰지 않는다(식과 설명만). 서버가 코드 블록 여부, 팀이 보유한 검증 정답 코드와의 유사도, 문제 태그의 알고리즘명 노출을 검사하고, 위반하면 한 번 다시 생성한다. 다시 위반하면 결과를 보여 주지 않는다. 검증 정답 코드는 테스트 생성과 이 검사에만 쓰고 사용자에게는 보여 주지 않는다.
  - 검사(`AnswerGuard`)는 응답의 글마다 코드 블록, 들여 쓴 코드 줄, 함수 호출·선언·반복문 머리 같은 코드 모양, 검증 정답 코드와 이어서 8토큰 이상 같은 조각(코드에만 쓰는 기호가 2개 이상 있을 때), 문제 태그의 알고리즘 이름과 그 다른 이름(예: 동적 계획법·DP)을 본다. 학습자 코드를 그대로 옮긴 글, 지문에 이미 나온 이름, 반복문·조건문처럼 알고리즘 이름이 아닌 태그는 위반으로 보지 않는다. F3 코드 리뷰에는 알고리즘 이름 규칙을 쓰지 않는다(6절).
  - 다시 만들 때는 어긴 규칙을 알려 주고 지시를 강화한다(`prompts/analysis-<버전>/retry.md`, `prompts/code-review-<버전>/retry.md`). 다시 만든 응답도 걸리면 차단 표시만 저장한다(`database-schema.md`). 검사 결과는 `answer-guard` 로그에 한 줄씩 남겨(`type=ANALYSIS|CODE_REVIEW`) 품질 평가에서 위반·재생성·차단 건수를 센다.
- **비공개 테스트 보호**: 비공개 입력·출력 원문은 AI에 전달하지 않고 응답에도 나오지 않는다. 응답에 비공개 값으로 보이는 글이 있는지는 아래 사실 검증이 본다.
- **사실 검증**: [사실]로 표시된 항목은 서버가 실행 결과와 대조하고, 줄 번호는 실제 코드 범위 안에 있어야 한다. 정답 코드 검사를 통과한 응답을 저장하기 전에 서버(`FactCheck`)가 고친다. 이 검사로는 다시 생성하지 않는다(#79).
  - 줄 번호: 1부터 제출 코드의 전체 줄 수까지가 맞는 번호다(모델에 300줄까지만 보내도 범위는 전체 줄 수다). 의심 줄(`suspectLines`)에서 벗어난 번호를 지우고, [사실]·[추정]·F3 개선점 중 벗어난 줄("N번째 줄", "N~M번 줄", "N행")을 짚은 항목은 지운다(추정으로 옮기지 않는다). 지울 수 없는 요약·힌트·F3 복잡도와 다음 개념의 글은 그대로 두고 건수만 센다. "출력의 3번째 줄", "예제 1에서 2번째 줄", "12번째 줄부터 다릅니다"처럼 출력의 줄일 수 있는 표기와, "100번 줄어듭니다", "100번 줄었습니다", "1000번 줄일 수 있습니다", "2번째 줄바꿈"처럼 "줄"로 시작하는 다른 말은 보지 않는다("N번 라인"에는 이 예외를 쓰지 않는다). "코드의 9번째 줄"처럼 코드라고 밝혔거나 "45번 줄에서 달라집니다"처럼 값이 바뀐다는 말은 코드 줄로 본다.
  - [사실] 대조: 모델이 받은 입력(판정, 런타임 에러 종류, 공개 예제의 입력·기대 출력·실제 출력·에러 메시지, 컴파일 메시지, 비공개 테스트 요약, 실행 시간·메모리)에 기댄 말이 하나도 없거나, 입력과 어긋나면 그 항목을 [추정] 끝으로 옮긴다. 문장은 고치지 않는다. 어긋남은 컴파일 에러인데 예제 실행 결과를 말함, 입력에 없는 예제 번호, "예제 모두 통과·실패"가 개수와 다름, 비공개 요약이 없는데 비공개 결과를 말함, 비공개 개수가 다름, "가장 작은·큰 입력" 서술이 입력과 반대이거나 크기를 가릴 수 없음, 입력에 없는 판정 이름(시간 초과·메모리 초과·런타임 에러·컴파일 에러·출력 형식·출력 초과)이다. 두 자리 이상의 수·음수·소수와 따옴표 안의 글은 모두 입력에 있어야 한다(지문의 수는 실행 결과가 아니다). 그래서 [사실]이 비고 [추정]이 10개까지 늘 수 있다.
  - 비공개 값: 비공개 케이스의 입력·기대 출력 줄과 그 4개씩 이어진 값 조각이 응답에 있으면 그 항목을 지우고, 요약·힌트에 있으면 결과를 차단한다. 값은 수·영문 낱말·기호 묶음 단위로 맞춰 보므로 `**IMPOSSIBLE**`, `answer=6227020800;`, `[100,200,300,400]`처럼 기호가 붙어도 같은 값이다. 천 단위 쉼표는 지운 형태와 지우지 않은 형태를 둘 다 본다. 6자 미만(값 하나면 8자 미만), 같은 값의 되풀이, 1씩 늘거나 주는 정수열, 기호로만 된 값(`*********`), 자료형의 한계와 자주 쓰는 나머지 연산의 수(`2147483647`, `1000000007` 등 값 하나짜리), 학습자가 이미 볼 수 있는 글(지문, 공개 예제와 그 실행 출력, 제출 코드, 컴파일 메시지)에 있는 값은 보지 않는다. 길이·되풀이·정수열은 기호를 뺀 값으로 본다(`[1, 2, 3, 4, 5]`도 정수열이다). 값이 모두 한 글자인 줄과 조각(`3 1 4 2`, `0 1 1 0`)은 모델이 지어낸 예시와 우연히 같기 쉬우므로, 값이 8개 이상이고 서로 다른 값이 3개 이상일 때만 보고 조각도 8개씩 자른다. 한글이 섞인 줄은 줄 전체를 후보로 삼고, 응답과 공개 글 모두에서 글 안에 들어 있는지(부분 문자열)로 맞춘다. 지문의 지수 표기(`10^9`, `2 × 10^5`, `10⁹`, `10<sup>9</sup>`, `1e9`, `10^9 + 7`)는 그 수로도 공개 값에 넣어, 제약의 최대값이 비공개 입력과 같아도 비공개 값으로 보지 않는다. 케이스마다 앞 4,000자까지 보고, 후보는 2,000개(한글이 섞인 후보는 그중 300개), 살펴보는 조각은 20,000개까지다(정답 값이 먼저 들어가게 기대 출력부터 뽑는다). "N번째 비공개 테스트"처럼 순서를 말한 항목도 지운다(요약·힌트는 센다). 값을 바꾸거나 재배열한 누출까지 잡지는 않는다. 이 수치는 #79에서 정한 처음 값이고, 한 글자 값과 흔한 수의 예외는 병합 뒤 검수에서 오탐을 확인해 넣었다.
  - 검증 내역은 `ai_reviews.content`의 `factCheck`(규칙 버전, 지운·옮긴·그대로 둔 건수, `규칙@위치` 목록)에 저장하고(규칙 버전은 같은 응답의 결과가 달라지게 규칙을 바꿀 때 올린다. #223에서 2가 됐다) API 응답에는 넣지 않는다. `fact-check` 로그에도 한 줄씩 남긴다. 둘 다 응답 글과 비공개 값은 남기지 않는다. #79 전에 저장한 결과는 다시 검증하지 않는다(`factCheck`가 없다). 화면은 그 결과를 위해 범위 밖 줄 번호를 계속 거른다.
  - F3 코드 리뷰는 정답 제출이라 예제·비공개 테스트를 보내지 않으므로 줄 번호 범위만 본다.
- **호출 한도와 비용**: AI 분석(F1+F2)과 리뷰(F3)는 합쳐 사용자당 하루 20회(서버 설정 `LLM_DAILY_LIMIT`)까지 쓸 수 있다. 하루는 UTC 날짜다(한국 시각 오전 9시에 초기화). 새로 만들기 시작할 때만 세고, 힌트 단계를 여는 것과 저장된 결과를 다시 받는 것은 추가 호출이 아니다. 만들지 못한(`FAILED`) 결과는 세지 않는다(세는 기준은 `database-schema.md`). 서버가 처리 중에 내려가 `PENDING`으로 남은 결과는 응답에서는 `FAILED`로 보이지만 DB에는 `PENDING`이라 다시 요청하기 전까지 1회로 센다. 다시 요청하면 같은 행이라 횟수가 늘지 않는다. 남은 횟수는 분석·리뷰 응답의 `quota`와 `GET /api/users/me/ai-quota`로 주고, 다 쓰면 429 `AI_DAILY_LIMIT_EXCEEDED`와 다음 초기화 시각을 준다. 리포트(F4)는 하루 1회이고 이 한도에는 세지 않는다. 같은 제출·같은 프롬프트 버전의 결과는 재사용한다. AI는 버튼을 눌렀을 때만 호출하므로 오답마다 자동으로 호출하던 이전 설계보다 호출 수가 적다.
- **장애 대응**: AI 장애나 한도 초과 시에도 채점, 예제 실행, 학습 기록은 정상 동작한다(#81).
  - 만들지 못한 결과는 `FAILED`와 그 이유 `failureReason`으로 준다. `UNAVAILABLE`은 AI 서버 장애(타임아웃·연결 실패·5xx·미설정, 처리 중 서버가 내려간 경우 포함), `RATE_LIMITED`는 AI 서버의 요청 한도(429), `BUSY`는 이 서버의 AI 대기열이 찼거나 한 사용자가 동시에 만들 수 있는 수(`LLM_USER_CONCURRENCY`, 기본 3)를 넘음, `INVALID_RESPONSE`는 다시 요청해도 형식에 맞지 않는 응답, `INTERNAL`은 그 밖의 서버 오류다. 오늘 한도를 다 쓴 것은 결과가 아니라 요청을 429 `AI_DAILY_LIMIT_EXCEEDED`로 거절한다. 화면은 이 구분으로 안내 문구를 고른다(AI-06). 화면 쪽은 아직 한 문구다.
  - 어느 이유든 같은 버튼을 다시 누르면 같은 행으로 다시 만든다(AI-02). `FAILED`는 하루 한도에 세지 않는다.
  - 서버가 스스로 다시 부르는 것은 스키마를 어긴 응답 1회와 정답 코드가 섞인 응답 1회뿐이라 요청 한 번에 모델 호출은 최대 4회다. 타임아웃·5xx·429에는 다시 부르지 않는다. 응답을 못 받은 호출은 모델이 아직 만들고 있을 수 있어, 다시 부르면 팀 서버에 일이 쌓인다.
  - 달러 예산은 두지 않는다. 팀 서버의 오픈 웨이트 모델이라 호출당 요금이 없고, 모델 서버의 부담은 동시 호출 수(`LLM_WORKERS`)와 대기열(`LLM_QUEUE_CAPACITY`)로 묶는다. 대기열이 차면 기다리게 하지 않고 바로 `BUSY`로 답한다. 한 사용자가 서로 다른 제출로 대기열을 혼자 채우지 못하게, 사용자마다 만드는 중인 분석·리뷰는 `LLM_USER_CONCURRENCY`개(기본 3, 1 이상)까지만 받고 넘으면 같은 `BUSY`로 답한다. 서버가 뜬 뒤에 시작한 것만 세므로, 서버가 내려가 남은 `PENDING`은 세지 않는다.
  - AI 호출은 채점과 다른 스레드(`ai-*`)에서 돌고, 모델을 기다리는 동안 DB 연결을 쥐지 않는다. 그래서 모델이 응답하지 않거나 대기열이 차도 채점 상태·결과, 예제 실행, 제출 기록, 학습 통계 조회는 기다리지 않는다. `AiIsolationTest`가 DB 연결 2개로 이를 확인한다.

## 10. 채점 결과와 쉬운 설명 (AI 없이 표시)

판정 종류와 공개 범위는 백준 온라인 저지를 따른다. 제출 후 “기다리는 중 → 채점 준비 중(컴파일) → 채점 중(진행률 %)”을 거쳐 아래 결과 중 하나가 나오며, 결과 화면에 쉬운 설명과 먼저 확인해 볼 점을 함께 보여 준다.

| 결과 | 쉬운 설명 (화면 문구) | 먼저 확인해 볼 것 |
|---|---|---|
| 맞았습니다!! | 모든 테스트에서 정답과 똑같이 출력했어요. | [AI 리뷰]로 더 빠르거나 읽기 쉬운 방법이 있는지 확인해 보세요. |
| 출력 형식이 잘못되었습니다 | 답의 내용은 맞았지만 띄어쓰기나 줄바꿈이 문제에서 요구한 모양과 달라요. | 줄 끝에 남은 공백, 빠지거나 더해진 빈 줄, 숫자 사이 구분 문자를 예제 출력과 한 글자씩 비교해 보세요. |
| 틀렸습니다 | 프로그램은 끝까지 실행됐지만, 어떤 입력에서 정답과 다른 값을 출력했어요. | 가장 작은 입력과 가장 큰 입력, 빠뜨린 조건, 값이 자료형 범위를 넘는지 확인해 보세요. |
| 시간 초과 | 정해진 시간 안에 프로그램이 끝나지 않았어요. 답이 맞는지는 아직 확인하지 못했어요. | 입력이 가장 클 때 반복이 몇 번 도는지 계산하고, 끝나지 않는 반복이 없는지 확인해 보세요. |
| 메모리 초과 | 허용된 메모리보다 많이 사용했어요. | 배열·리스트의 크기와 재귀 호출의 깊이를 확인해 보세요. |
| 출력 초과 | 정답보다 훨씬 많은 양을 출력했어요. | 출력하는 반복문이 제때 끝나는지, 디버깅용 출력이 남아 있지 않은지 확인해 보세요. |
| 런타임 에러 (종류) | 실행 도중 프로그램이 멈췄어요. 괄호 안이 멈춘 이유예요. | 아래 종류별 설명을 확인해 보세요. |
| 컴파일 에러 | 실행하기 전 문법 검사에서 막혔어요. 결과를 누르면 몇 번째 줄에서 무엇이 문제인지 알려 주는 메시지를 볼 수 있어요. | 괄호·세미콜론·들여쓰기, 선언하지 않은 변수, 제출 언어를 제대로 골랐는지 확인해 보세요. |
| 채점 불가 | 서버 문제로 채점하지 못했어요. 내 코드의 문제가 아니에요. | 잠시 후 다시 제출해 주세요. 이 제출은 시도 횟수에 넣지 않아요. |

**런타임 에러 종류별 설명**

| 표시 | 쉬운 설명 |
|---|---|
| IndexError / Segfault | 리스트·배열에 없는 칸을 읽거나 썼어요(C++의 Segfault는 잘못된 메모리 접근 전반). 반복 범위와 배열 크기를 비교해 보세요. |
| ZeroDivisionError / DivisionByZero | 0으로 나눴어요. 나누는 값이 0이 되는 입력이 있는지 확인해 보세요. |
| ValueError | 값의 모양이 맞지 않아 변환하지 못했어요. 한 줄에 숫자가 여러 개인데 `int(input())`으로 읽지 않았는지 확인해 보세요. |
| NameError | 만들지 않은 변수나 함수 이름을 썼어요. 오타와 대소문자를 확인해 보세요. |
| TypeError | 서로 다른 종류의 값끼리 계산했어요(예: 문자열 + 숫자). |
| RecursionError / StackOverflow | 재귀 호출이 너무 깊어요. 종료 조건이 있는지, 깊이가 입력 크기만큼 커지지 않는지 확인해 보세요. |
| EOFError | 주어진 입력보다 더 많이 읽으려 했어요. 입력 줄 수를 다시 확인해 보세요. |

**판정 규칙**

- 출력 비교: 줄바꿈 문자(CRLF)와 출력 끝의 줄바꿈 한 개만 통일한 뒤 비교한다. 공백·줄바꿈만 다르면 ‘출력 형식이 잘못되었습니다’, 공백을 모두 지워도 다르면 ‘틀렸습니다’다.
- 런타임 에러 이름: Judge0가 돌려주는 신호(SIGSEGV·SIGFPE 등)와 Python 예외 이름을 위 표의 이름으로 바꿔 표시한다. Judge0 응답을 판정과 에러 이름으로 바꾸는 세부 규칙은 [`judge-verdict-mapping.md`](judge-verdict-mapping.md)에 있다.
- 비공개 테스트에서 난 런타임 에러는 종류만 보여 준다. 입력값이 섞일 수 있는 메시지 원문과 줄 번호는 공개 예제 케이스에서만 보여 주고 AI에도 그 범위만 전달한다(예제 실행과 제출 결과 모두). 제출 채점은 공개 예제부터 실행해, 예제에서 난 에러를 먼저 보여 줄 수 있게 한다.
- 채점 서버 오류는 학생의 오답이 아니라 ‘채점 불가’로 표시하고 시도 횟수에서 뺀다.
