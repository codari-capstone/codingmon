# 데이터베이스 스키마 초안

PostgreSQL용 초안이다. DDL은 `api/src/main/resources/db/migration/V1__initial_schema.sql`에 있다. 시간은 UTC `timestamptz`, 테이블·컬럼은 복수형·`snake_case`로 쓴다. API를 기동하면 Flyway가 V1을 자동 적용한다.

## 테이블과 역할

### 계정과 로그인

| 테이블 | 주요 데이터 | 역할 |
| --- | --- | --- |
| `users` | 이메일, 비밀번호 해시, 고유 닉네임, 프로필 이미지, 권한 | 서비스 내부 사용자와 프로필 |
| `oauth_accounts` | 사용자, 제공자, 제공자 계정 고유 ID | GitHub 계정 연결. GitHub 사용자명 대신 변하지 않는 제공자 ID로 식별 |
| `refresh_tokens` | 사용자, 토큰 해시, 토큰 묶음 ID, 만료·폐기 시각 | 로그인 유지, 갱신, 로그아웃 및 토큰 폐기 |
| `email_tokens` | 이메일, 용도, 인증번호 해시, 시도 횟수, 만료·사용 시각 | 가입 전 이메일 인증번호 발송·확인과 재발송 제한 |

일반 가입은 이메일과 `password_hash`를 사용하고, OAuth 가입은 `oauth_accounts`에 계정 연결을 만든다. OAuth access token과 refresh token 원문은 저장하지 않는다. `nickname`은 사용자 요청에 따라 대소문자 구분 없이 중복을 허용하지 않는다. 사용자 행에는 생성·변경 시각 컬럼을 두지 않는다.

`users` 행은 가입 완료 시점에만 만든다. 인증하지 않은 사용자는 `users`에 남지 않는다.

- **일반 가입**: 한 화면에서 이메일 인증, 닉네임 중복 확인, 비밀번호 입력을 모두 마쳐야 \[가입 완료\]가 활성화된다. 이메일 중복 확인은 인증번호 발송 요청에서 함께 한다.
  1. 인증번호 발송: 이미 가입된 이메일이면 보내지 않고 안내한다. 같은 이메일로는 1분 간격, 하루 5회까지 보낼 수 있다. 새로 보내면 이전 인증번호는 `used_at`을 채워 무효로 한다.
  2. 인증번호 확인: 6자리 인증번호는 5분 뒤 만료되고, 5회 틀리면 무효가 된다. 맞으면 `used_at`을 채우고 서버 서명 인증 증명서(이메일 포함, 30분 유효)를 응답한다. 증명서는 DB에 저장하지 않는다.
  3. 가입 완료: 증명서의 서명·만료와 이메일 일치를 확인한 뒤 `users`에 INSERT한다.
- **GitHub 가입**(부가 가입 수단): GitHub 인증이 이메일 인증을 대신하고, 서버는 인증 결과(GitHub 계정 ID·인증된 이메일)를 담은 증명서를 같은 방식으로 발급한다. 이어지는 화면에서는 닉네임만 입력한다(GitHub 사용자명을 기본값으로 제시). 비밀번호는 만들지 않으며 `password_hash`는 비워 두고 GitHub로만 로그인한다. GitHub 가입 계정으로 이메일 로그인을 시도하면 GitHub 로그인을 안내한다. 이메일은 GitHub가 인증한 이메일만 저장하고, 없으면 비워 둔다.
- **가입 완료 시 닉네임 충돌**: 두 가입 방식 모두 닉네임 중복 확인 이후 다른 사람이 같은 닉네임으로 먼저 가입했으면 유일 인덱스 위반으로 실패한다. 증명서가 유효한 동안 닉네임만 다시 입력받는다.
- **같은 이메일 충돌**: 일반 가입과 GitHub 가입이 같은 이메일로 겹치면 자동으로 연결하지 않고 거부한 뒤, 기존 방식으로 로그인하도록 안내한다.
- **비밀번호 규칙**: 8~20자이며 영문 대문자·소문자·숫자·특수문자를 각각 하나 이상 포함한다. DB 제약이 아니라 서버와 화면에서 검사한다.

### 문제와 채점

| 테이블 | 주요 데이터 | 역할 |
| --- | --- | --- |
| `problems` | 안정적인 문제 slug | 버전이 바뀌어도 유지되는 문제 식별자 |
| `problem_versions` | 제목, 난이도, 지문, 입출력 설명, 제약, 출처·라이선스, 공개 상태 | 수정 이력을 보존하는 문제 콘텐츠 |
| `problem_language_configs` | 버전, 언어, 시간·메모리 제한, 시작 코드 | Python/C++별 풀이 설정 |
| `concept_tags` | 태그 이름과 slug | 리포트 통계에 쓰는 개념 분류 |
| `problem_version_tags` | 문제 버전과 태그 연결 | 버전별 개념 태그 연결 |
| `test_cases` | 버전, 순서, 공개/비공개 구분, 입력·기대 출력 | 예제 실행 및 채점 테스트 데이터 |
| `reference_solutions` | 버전, 언어, 역할, 검증 정답 코드 | 채점기·검증 내부 전용 정답 코드 |
| `submissions` | 사용자, 문제 버전, 실행 종류, 언어, 소스 코드, 채점 상태·판정·자원 사용량 | 예제 실행과 제출 기록 |
| `submission_test_results` | 제출, 테스트 케이스, Judge0 토큰, 판정, 시간·메모리, 공개 예제의 stdout/stderr | 케이스별 채점 상태와 결과. 비공개 케이스의 출력 원문은 저장하지 않음 |

문제 내용과 태그는 버전 기준으로 보존한다. 문제별 언어 설정은 버전마다 등록한다. 비공개 테스트와 정답 코드는 공개 저장소에 데이터로 커밋하지 않는다. 실제 값은 비공개 `problems` 저장소를 원본으로 관리하고 API 응답에 포함하지 않는다.

### AI와 학습 기록

| 테이블 | 주요 데이터 | 역할 |
| --- | --- | --- |
| `ai_reviews` | 제출, 분석/리뷰 종류, 모델·프롬프트 버전, JSON 응답, 사용량·비용, 공개한 힌트 단계 | 오답 분석과 정답 코드 리뷰 결과 저장 및 재사용 |
| `review_feedback` | AI 리뷰, 도움 여부, 이유 | 사용자가 남긴 피드백 |
| `user_problem_stats` | 사용자·문제, 해결 여부·최초 정답 시각, 시도 수, 힌트 단계 합계·분모 | 리포트용 집계값. 제출과 AI 기록에서 다시 계산 가능 |
| `learning_reports` | 사용자, 기준 날짜, 통계 JSON, AI 결과 JSON, 모델·상태 | 사용자별 일일 리포트 |
| `learning_report_recommendations` | 리포트, 순위, 문제 버전, 태그, 추천 이유 | 추천 목록과 순서를 정규화해 보존 |

분석·리뷰 일일 한도(합쳐서 하루 20회)는 사용자의 제출에 오늘 만들어진 `ai_reviews` 행 수로 센다. 재사용한 결과는 새 행이 생기지 않으므로 횟수에 들어가지 않는다. AI 실패는 사용자 책임이 아니므로 `FAILED` 행은 횟수에서 뺀다. `FAILED` 행이나 AI 호출 제한 시간이 지나도 끝나지 않은 `PENDING` 행을 재시도할 때는 유일 제약 때문에 새 행을 만들지 않고 기존 행을 `PENDING`으로 UPDATE하며, `created_at`을 재시도 시각으로 갱신한다. 그래서 재시도는 재시도한 날의 횟수로 잡히고, 같은 날 여러 번 재시도해도 결과 1건으로 센다. 실패한 호출의 토큰·비용은 재시도 결과로 덮어써져 남지 않는다. 리포트 하루 1회는 `learning_reports`의 유일 제약이 막는다. 별도 AI 호출 기록 테이블은 두지 않는다. `user_problem_stats`의 평균 힌트 단계는 `revealed_hint_level_sum / hinted_submission_count`로 계산한다. 힌트를 열지 않은 제출을 평균에 포함할지 여부는 통계 정의에서 확정한다.

## 중요한 제약과 남은 결정

- 이메일은 소문자로 정규화하고 대소문자를 구분하지 않는 유일 인덱스로 중복 가입을 막는다. GitHub에서 이메일을 받지 못한 OAuth 계정은 이메일 없이도 생성할 수 있다.
- 사용자 계정은 비밀번호 로그인, OAuth 계정 중 적어도 하나가 연결되어 있어야 한다. OAuth 계정 연결/해제 시 마지막 로그인 수단을 제거하지 못하게 서비스에서 검증한다.
- `nickname`은 대소문자를 구분하지 않고 유일하다. 가입·변경 화면의 중복 확인은 안내용이며 닉네임을 미리 점유하지 않는다. 최종 판정은 가입 완료(또는 변경 저장) 시점의 INSERT/UPDATE에서 `users_nickname_lower_idx`가 하고, 충돌하면 "이미 사용 중"으로 안내한다.
- 회원 탈퇴 시 사용자 행을 삭제하고, 사용자에 딸린 데이터(OAuth 연결, 토큰, 제출, 케이스 결과, AI 결과·피드백, 통계, 리포트)는 함께 삭제한다.
- 문제당 게시 버전은 하나만 허용한다. 새 버전을 공개할 때는 같은 트랜잭션 안에서 기존 버전을 먼저 `RETIRED`로 바꾼 뒤 새 버전을 `PUBLISHED`로 바꾼다. 유일 인덱스는 지연 검사가 되지 않아 순서가 바뀌면 실패한다. `PUBLISHED` 버전은 `published_at`이 있어야 한다.
- 게시된 버전의 테스트 케이스는 추가·수정·삭제하지 않는다. 케이스를 바꾸려면 새 버전을 만들어 게시한다. 기존 제출은 원래 버전과 그 케이스를 계속 가리켜 판정·출력 기록이 유지되고, 새 제출만 새 버전으로 채점된다. 풀이 여부(`user_problem_stats`)는 문제 단위라 버전이 바뀌어도 유지된다. 제출 결과가 있는 케이스는 `ON DELETE RESTRICT`로 삭제가 막힌다. 초안 버전은 제출이 없어 케이스를 자유롭게 편집할 수 있다.
- Judge0는 테스트 케이스마다 토큰을 발급하므로 토큰은 `submission_test_results.judge_token`에 저장한다. 케이스를 채점 서버에 보낼 때 판정 없이 행을 만들고, 결과를 받으면 판정을 채운다. 컴파일 에러나 채점 서버 오류로 제출이 끝나면 실행하지 않은 케이스 행은 판정이 빈 채로 남으므로, 케이스 판정은 항상 `submissions.job_status`와 함께 해석한다. API가 재시작되면 `job_status`가 진행 중(`QUEUED`/`COMPILING`/`RUNNING`)인 제출을 찾는다. 실행 대상 케이스(예제 실행은 `SAMPLE`, 제출은 전체) 중 행이 없거나 토큰이 빈 케이스는 채점 서버에 다시 보내고, 판정이 빈 행은 토큰으로 다시 조회한다. 실행 대상 케이스 전부의 판정이 채워졌을 때만 제출의 최종 판정을 계산해 마무리한다.
- `stdout`/`stderr`는 `SAMPLE` 케이스에만 저장한다. 서비스에서 최대 길이(65,536자)로 잘라 저장한다.
- 버전별 태그 1~3개, 게시 조건(공개 예제 2개 이상·비공개 테스트 5개 이상·2개 언어 정답 검증·출처 입력)은 여러 행에 걸친 조건이라 DB 제약만으로 표현하지 않고 게시 서비스에서 검증한다.
- `submission_test_results`의 공개 예제 결과는 예제 실행에서는 판정·stdout·stderr를 모두 보여 주고, 제출 결과에서는 에러 원문(stderr)만 보여 준다. 제출의 공개 예제 stdout은 AI 분석 입력으로만 쓴다. 비공개 케이스의 입력, 기대 출력, 케이스 순번이나 실패 여부는 사용자 API에서 노출하지 않는다.
- AI 응답 JSON의 필드 구조, 사실/추정 근거, 줄 번호 검증은 API 계약과 함께 정의한다. 힌트 본문이 저장되어도 사용자가 연 단계까지만 반환한다.
- 리포트는 사용자 시간대 정책에 따라 `report_date`를 계산한다. 현재 초안은 사용자당 하루 한 건을 유일 제약으로 막는다.
- 추천행은 문제 버전이 해당 문제에 속하는지, 추천 근거 태그가 그 버전에 실제 연결되어 있는지 외래 키로 확인한다.
- `email_tokens`는 사용자 행이 생기기 전에 쓰므로 `users`를 참조하지 않고 이메일로 조회한다. 이메일별·용도별로 유효한(`used_at`이 빈) 인증번호는 하나만 허용한다. 재발송 제한은 하루 단위로 세므로 하루가 지난 행은 정리해도 된다.
- 초대 코드 기능은 두지 않는다.
- develop에 병합되기 전까지는 V1을 수정할 수 있다. 그 기간에 로컬 DB에 V1을 적용했다면, V1이 바뀐 뒤 로컬 DB를 초기화한다. 병합 후에는 기존 파일을 고치지 않고 다음 버전 마이그레이션을 추가한다.
